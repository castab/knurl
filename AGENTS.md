# AGENTS.md — Knurl

Context-seeding notes for AI coding agents working in this repo. Read this before making structural changes.

## Hard constraint: low-memory streaming

`ingestion-service` runs with a **512MB heap** (`-Xmx512m`, set in its Dockerfile) because it is an ephemeral sync job that decodes images and probes video containers. `presentation-service` retains its 128MB deployment target. The larger ingestion heap is capacity, not permission to buffer unbounded payloads: its HikariCP pool stays capped at `maximumPoolSize = 2` / `minimumIdle = 1` (see `shared-domain/.../config/DatabaseSettings.kt`), and bounded coroutine concurrency via a `Semaphore` + the shared `Dispatchers.IO` dispatcher remains required (see `runEviction`/`fetchThumbnailsConcurrently`). Don't add a dedicated/unbounded thread pool or unbounded coroutine concurrency.

**Never buffer a full media payload in a `ByteArray`/`ByteArrayOutputStream`.** Specifically:

- Video: `MediaProcessor.processVideoPassthrough` streams the OkHttp response body directly into the S3 `RequestBody` when `Content-Length` is known. The same stream is mirrored into `ffprobe` so its actual container dimensions can be persisted, but neither consumer retains a full payload in the JVM. If the length is unknown (chunked CDN response), it spills to a local temp file (disk, not heap) and uploads from that file — this is the one sanctioned fallback, not a buffering shortcut. Don't "simplify" this by reading the whole video into a `ByteArray` first.
- Images: `MediaProcessor.processImage`/`processThumbnail` decode the source image into memory via Scrimage, produce two WebP variants at 80% quality — a 400×400 grid thumbnail (`squareVariant`, scale-and-center-crop, because every grid cell that consumes it is a fixed `aspect-ratio: 1 / 1`) and an 800px detail image (`boundedVariant`, scaled to fit inside an 800×800 box with the source aspect ratio intact, so at most 800×800 and never upscaled) — and upload the *compressed output only* (tens of KB) as bytes. This is a **documented, bounded exception** — any resize operation requires an in-memory raster at some point. The bound is enforced in `MediaProcessor.downloadImage`, which rejects a source whose declared `Content-Length` exceeds `MAX_SOURCE_IMAGE_BYTES` before decoding; a decoded raster is roughly `width * height * 4` bytes and is otherwise unbounded. Don't try to eliminate the exception; don't remove that ceiling; don't add more image variants without checking the memory cost.
- Video has its own ceiling for a different reason - `MAX_SOURCE_VIDEO_BYTES` (100MiB) isn't a heap-OOM guard (nothing here decodes a video into memory), it bounds the temp-file fallback's disk usage. The known-length branch checks the declared `Content-Length` upfront (same pattern as images); the unknown-length branch has no declared length to check, so `copyWithLimit` counts bytes while streaming to the temp file and aborts past the limit. Don't remove either check, and don't replace `copyWithLimit`'s counted copy with a plain `InputStream.copyTo`.

If you're adding a new remote-asset code path, follow the same pattern: OkHttp response `.byteStream()` piped straight into the AWS SDK's streaming `RequestBody`, never fully materialized first.

## Architectural boundaries

- **`presentation-service`'s database writes are bounded and enumerable**: the per-gallery analytics counters on `gallery_items` (`POST .../galleries/{galleryId}/track`), the `galleries` and `gallery_items` rows managed by `AdminGalleryRoutes`, and the deletion clock (`deselected_at`/`purge_requested_at`) maintained alongside every membership change and by `DELETE .../catalog/media`. It never runs Flyway migrations and never calls the Meta Graph API.
- **Galleries widened that boundary on purpose, and the widening has a limit worth stating.** Going from "toggle one boolean" to full CRUD on a first-class entity is a real extension, justified by the same fact as before: `ingestion-service` opens no HTTP listener, so admin intent has to be recorded here and collected from the shared database on the next cycle. The part that has *not* moved is the one that matters — **presentation-service still issues no S3 call at all** beyond presigning reads. Every byte deletion remains ingestion's. Keep any future admin surface on that side of the line.
- **`presentation-service` never touches the bucket except to presign reads.** `DELETE .../catalog/media` looks like an outright delete but only records intent in the database; `ingestion-service` performs every actual S3 deletion on its next cycle. That is why the endpoint answers `202` with an `acceptedCount` rather than `200` with a `deletedCount` — when the response is written, the bytes are still there. Keeping it this way is what keeps destructive bucket calls out of the internet-facing service; don't "fix" the latency by handing `presentation-service` an `S3Client`.
- **`ingestion-service` never opens an HTTP listener** or accepts inbound traffic. It owns the schema — it's the only service that calls `DatabaseConfig.runMigrations`. This is why admin curation flows through `presentation-service` writing a flag in the shared database rather than `ingestion-service` exposing an API of its own — see "Multi-account model" below.
- **`shared-domain` has zero HTTP/JSON-framework dependency.** It doesn't know about http4k, kotlinx.serialization, or Hoplite. `presentation-service` defines its own `@Serializable` response DTOs (`routes/GalleryRoutes.kt`) and maps domain models to them explicitly — don't add serialization annotations to `knurl.domain.models.*`.
- **No application framework.** No Spring Boot, Micronaut, Ratpack, or DI container. Both `Main.kt` files manually construct and wire every collaborator (`HikariDataSource`, `Jdbi`, `OkHttpClient`, `S3Client`, repositories) by hand. Keep it that way — don't introduce a DI library or component-scanning.

## IDs and the database

- `instagram_posts.id` is a **surrogate** primary key — `UUID PRIMARY KEY DEFAULT uuidv7()`, generated by Postgres (18+, native function, no extension). Application code never invents this value; it's read back from the database.
- `instagram_posts.instagram_media_id` is the **natural key** from Meta's Graph API. It's what `SyncPipeline` upserts against (`ON CONFLICT (instagram_media_id)`) and what S3 object key prefixes are built from (`posts/{instagram_media_id}/...`) — this is deliberate, since the media id is known before a database row exists and the surrogate `id` isn't. It and `instagram_media_catalog.shortcode` stay **globally unique**, not composite-keyed with an account, since Meta's ids/shortcodes are unique platform-wide.
- The Kotlin domain type for `id` is `kotlin.uuid.Uuid` (the stable stdlib type, not `java.util.UUID`). JDBI doesn't support it natively — `shared-domain/.../config/KotlinUuidSupport.kt` registers the bridging `ArgumentFactory`/`ColumnMapper`. If you add another `Uuid`-typed column, this bridge already covers it; you don't need to register anything per-repository.
- `InstagramPostRepository.upsert` takes an `InstagramPostUpsert` (no `id`/`createdAt` fields), not the full `InstagramPost` — those two columns are always left to their Postgres defaults.
- `instagram_posts`, `instagram_media_catalog`, and `auth_config` all carry an `instagram_account_id` column now (see "Multi-account model" below) — any new table holding per-account data should follow the same pattern rather than assuming a single global tenant.

## Multi-account model

This schema and both services support multiple Instagram accounts sharing one database, with different tenancy shapes per service:

- **`ingestion-service` is account-agnostic, not one-process-per-account.** Any process's worker coroutines claim whichever account is due for a feed sync (`AccountClaimRepository`, `instagram_accounts.last_synced_at`/`sync_claimed_at`) or whichever items are pending download (`DownloadQueueRepository`, `pending_downloads`), via `FOR UPDATE SKIP LOCKED` claim-and-release statements - not a held transaction, and not an in-application semaphore. `SyncPipeline`'s `targetUserId` constructor field still scopes one instance's repository calls to one account, but that instance is now constructed fresh per claimed account per cycle by the feed-sync worker loop in `Main.kt`, not held for the process's lifetime. This is what actually lets several accounts be served by fewer, more efficient processes sharing one database - not just "nothing stops you," the intended shape.
- **Account *anchoring* stays single-account-per-process and is a distinct concept from claiming.** `instagram.businessAccountId`/`accessToken` anchor and seed exactly one account at startup (`accountRepository.ensureAccount(...)` in `Main.kt`), not a limit on which accounts this process's workers can subsequently claim and sync. Anchoring deliberately writes **no credentials** — it used to overwrite the account's presentation tokens from this process's env on every boot, which silently invalidated whatever a control plane had provisioned each time ingestion restarted. Don't reintroduce a token write here. A multi-account deployment runs in `CREDENTIALS_MODE=HTTP`, where `presentation-service` anchors a row per account its credential fetch returns.
- **`CREDENTIALS_MODE` is one flag with one meaning in both services** (`knurl.domain.config.CredentialsSettings`): `LOCAL` = self-sufficient from env/database, `HTTP` = a control plane owns all credential authority and knurl mints, rotates and decides nothing. Don't add a service-specific credential-source flag alongside it; the whole point of the unification was ending the state where ingestion had `INSTAGRAM_CREDENTIAL_PROVIDER` and presentation had an unrelated `PRESENTATION_PROVISIONING_TOKEN`.
- **Both credential providers (`DatabaseInstagramAccessTokenProvider`, `HttpBrokerInstagramAccessTokenProvider`) are account-parameterized**, not bound to one account at construction - `InstagramAccessTokenProvider.getAccessToken(accountId)` takes the account per call, since a single shared provider instance now resolves tokens for whichever account a worker is currently claiming work for. Don't reintroduce a constructor-level `accountId`/`expectedAccountId` field on either implementation.
- **Outbound credential-fetch hardening lives in `shared-domain`** (`knurl/domain/http/CredentialHttp.kt`): HTTPS-or-loopback URL validation, the 16 KiB response bound, the re-read-per-use bearer-token file, and `CredentialHttpException`, which must never carry a response body or token into its message. Both services build their fetch on it — don't duplicate any of it into a service module.
- **`presentation-service` is genuinely multi-tenant** — a single deployment serves every account that's been registered, with `accountId` (the Graph API business account id — public, non-secret, safe in a URL) as a path segment: `GET /api/v1/accounts/{accountId}/galleries[/{galleryId}]`, `GET /api/v1/admin/accounts/{accountId}/catalog`, and the gallery CRUD under `/api/v1/admin/accounts/{accountId}/galleries`.
- **Tenancy across `gallery_items` is enforced in SQL, not by a constraint.** Shortcodes are globally unique rather than per-account, so the add statement joins `galleries` *and* `instagram_media_catalog` to the same `instagram_account_id`; drop either half and one account can put another's media in its own public gallery. There is no composite FK backstopping this, so every new statement touching `gallery_items` has to remember both halves — `GalleryRoutePathBindingTest` and the cross-tenant check in the verification run are what keep it honest.
- **`instagram_accounts`** (`instagram_account_id PK`, `last_synced_at`, `sync_claimed_at`, `created_at`) is the tenant registry and **holds no credentials**. It once carried `admin_token_hash`/`read_token_hash`; those columns are gone, because two writers (ingestion's boot-time seed and a control plane's provisioning call) raced over them. Don't add a token column back here. Contrast `auth_config.access_token_encrypted`, which stays in the database and **is** recoverable (AES-256-GCM via `CredentialCipher`), because `ingestion-service` has to replay it to Meta's Graph API in `LOCAL` mode.
- **Presentation tokens live in memory, in `AccountCredentialStore`** (`presentation-service/.../credentials/`), as `TokenHasher.sha256` digests — one-way, since verification only needs to know whether a candidate *hashes to* the stored value. `LOCAL` mode fills the store from `ADMIN_TOKEN`/`READ_TOKEN` for one account; `HTTP` mode replaces it wholesale from the control plane on every fetch. Replacement is an `AtomicReference` whole-map swap, never a mutation of a live map: a request landing mid-replacement must not see an account momentarily absent and 404 it.
- **Both public gallery routes and admin routes are per-account, through the same mechanism now.** There is no shared, deployment-wide bearer token anymore (the old `BearerAuth`/`config.apiBearerToken`/`API_BEARER_TOKEN` are gone). `GalleryRoutes` and every admin route class share one helper, `authorizeAccount` in `routes/AccountAuth.kt` (renamed from `AdminAuth.kt` when this stopped being admin-only). Each request's `accountId` path segment is resolved to a `VerifyAccountToken` function - `AccountCredentialStore::verifyAdminToken` for admin routes, `::verifyReadToken` for gallery routes - which hashes the candidate bearer token and compares it against that account's stored hash: `404` for an unknown account, `401` for a real account with the wrong token, otherwise the route's real handler runs. **Never reuse one token across accounts** here; that's the whole point of per-account tokens, admin or read.
- **Route classes depend on `VerifyAccountToken` (a function type), not a concrete store or repository.** `GalleryRoutes`/`AdminGalleryRoutes`/`AdminCatalogRoutes` take a `(accountId, candidateToken) -> AccountTokenVerification` in their constructor, even though `Main.kt`/`GenerateOpenApiSpec.kt` always pass `credentialStore::verifyAdminToken`/`::verifyReadToken`. That indirection is what let the token source move out of the database entirely without touching a single route class — keep it.
- **`AdminAccountRoutes` is registered only in `HTTP` mode.** Its single bodyless `PUT /api/v1/admin/credentials/refresh` is the control plane's "credentials changed" signal; this service then re-fetches the authoritative set itself rather than trusting a pushed body, and replaces it **wholesale** because a per-account update cannot express that an account was removed.
- `sync_configurations` stays **global, not per-account** — every account's retention applies the same values independently within its own post pool (`InstagramPostRepository.findEvictionCandidates(accountId, ...)` scopes the query, not the values themselves). See "Object lifecycle" below for what those keys are.

## Object lifecycle

The governing invariant is that **the database knows about every object in the bucket**. Three mechanisms uphold it; changing one without the others will break it.

- **A gallery shows exactly its members.** `GalleryRepository.findContentPage` joins `gallery_items` to `instagram_posts`, so an item appears the moment it is added *and* downloaded, and disappears the moment it is removed. The post row and its S3 objects deliberately survive that removal, on a clock.
- **Membership in *any* gallery is what the old `selected` boolean was.** It gates the download (`mediaIdsInAnyGallery` → `shouldDownload`), protects a post from retention, and going false is what starts the clock. The `IN_ANY_GALLERY` constant is shared only by `findEvictionCandidates` and `deleteIfNotInAnyGallery`; it is **not** the visibility predicate any more, because visibility is per-gallery and reapability is any-gallery. "Invisible in gallery X but correctly not reaped" is now a normal state.
- **Retention is time-based.** `deselected_at` starts a `retention_days` countdown (default 30) when an item leaves its *last* gallery; `purge_requested_at` skips it entirely. Adding the item to any gallery clears both, which is what makes a re-add inside the window free — the media never left the bucket, so `existingMediaIds` still covers it and `shouldDownload` stays false.
- **`deselected_at` is a denormalisation, and it is defended twice.** It is maintained by four separate paths (add, remove, gallery delete, purge), so (a) every one of them takes `FOR UPDATE` on the catalog row *first* — without it two admins removing an item from two different galleries concurrently both see the other's uncommitted row, neither stamps, and the item leaks forever; and (b) `findEvictionCandidates` reads `COALESCE(c.deselected_at, p.created_at)`, so "in no gallery" is *sufficient* for eventual reaping however the clock was maintained. Both are load-bearing; the race is real and reproducible. Do not remove either.
- **Deletion order is DB row first, S3 second**, and the row delete (`deleteIfNotInAnyGallery`) re-checks membership so an item added back to a gallery mid-sweep wins. An S3-first ordering leaves a surviving row pointing at deleted media; row-first leaves an orphaned object, which the sweeper reaps. Don't flip it back.
- **`OrphanSweeper` deletes bucket objects the database has no record of.** Orphans are unavoidable — a carousel upload that fails partway strands its earlier children, a shrinking carousel strands its higher positions — and nothing else in the system can enumerate the bucket. Its guards each exist for a specific failure and should not be relaxed casually: an age threshold (`orphan_grace_minutes`) so an in-flight upload whose row isn't written yet is never mistaken for an orphan, a refusal to act when the database knows of no objects at all (a reset or wrong database would otherwise empty the bucket), a per-run cap, and a dry-run toggle.
- **`ObjectKeyRepository.allKnownKeys` is deliberately not account-scoped.** Object keys carry no account segment (`posts/{instagramMediaId}/...`), so a listing can't be attributed to an account and a per-account sweeper would delete its siblings' media. The corollary is a deployment constraint: **one bucket per database**.
- `is_pinned` defeats time-based retention but **not** an explicit purge request, and still has no write path anywhere in this repo — it is a manual-SQL-only escape hatch.
- **`SyncPipeline.removeVanishedMedia` deletes a catalog entry (and its post, if downloaded) the moment Instagram's own feed stops returning it.** This is a *different kind* of deletion from retention and deliberately skips every protection retention has — no grace period, no re-add race, no respect for `is_pinned` — because none of those make sense once the source of truth, not this system, is the one saying the media is gone. It only ever runs against the result of a *complete* pagination sweep: `syncCatalogAndSelectedMedia` returns the present-id set only after every page fetched without error, so a mid-pagination failure throws before this ever sees a partial listing. Because catalog rows cascade into `gallery_items`, a vanished item also leaves every curated gallery holding it — logged by name, since from an admin's side an item they picked by hand simply disappeared. `shouldSkipVanishedRemoval` is the one guard it does have — refuse to act when the vanished fraction looks too large to trust from a single cycle (rate limiting, a permissions hiccup, a bug returning a short page), below a small absolute floor so deleting an account's last few posts is never treated as suspicious.

Runtime knobs all live in `sync_configurations` rather than Hoplite config, so they can be changed without a redeploy: `retention_days` (30), `orphan_sweep_interval_hours` (24), `orphan_grace_minutes` (60), `orphan_sweep_max_deletes` (1000), `orphan_sweep_dry_run` (false), `vanished_media_max_percent` (50), plus `last_orphan_sweep_at`, which `SyncConfigurationRepository.claimIfElapsed` writes as **epoch seconds** (an ISO string would compare wrongly, since `Instant.toString()` drops a zero seconds field and `'Z' > '0'`).

## Configuration

### Instagram credential delivery

`SyncPipeline` obtains its Graph API token only through `InstagramAccessTokenProvider`; keep token storage, refresh, and delivery logic behind that boundary. Under `CREDENTIALS_MODE=LOCAL` the `DatabaseInstagramAccessTokenProvider` preserves standalone Knurl's behavior: `INSTAGRAM_ACCESS_TOKEN` seeds the first refresh and `auth_config` stores refreshed tokens AES-256-GCM-encrypted (`access_token_encrypted`, via `CredentialCipher` - see "Multi-account model" above) in the operator-owned database, transparently to `AuthConfigStore` callers. Under `HTTP`, the authenticated credential service owns refresh and persistence, and ingestion must neither consult nor update `auth_config`. Never add an HTTP-to-database fallback, since that would bypass control-plane-side revocation.

Renewing the Instagram access token against the Meta Graph API is the **one** credential operation knurl performs on its own, and only in `LOCAL` mode. Everything else — minting, rotating, deciding what is authorized — belongs to the control plane whenever one is present.

The broker request deliberately contains no account id. Its bearer credential is scoped to one account, and ingestion verifies the returned `instagramAccountId` against its configured account. HTTPS is the default; plaintext HTTP requires an explicit opt-in for trusted private service networks and never removes bearer authentication. Keep broker-specific HTTP code in `ingestion-service` — `shared-domain` remains free of HTTP/JSON-framework dependencies.

Both services load a typed config object from layered HOCON `.conf` resources via Hoplite — see `PresentationConfig`/`IngestionConfig`. **Don't reintroduce scattered `System.getenv(...)` calls** — add a field to the relevant config data class and reference it in a `.conf` file instead.

Hoplite's `addPropertySource` order is priority order: **the first source added wins** when a key is present in more than one, merged per key (not per file). Each `Main.kt` adds sources highest-priority-first:

- `ingestion-service`: `application.conf` (highest) → `application-instagram.conf` → `application-local.conf` (lowest)
- `presentation-service`: `application.conf` (highest) → `application-local.conf` (lowest)

`application.conf` is highest priority **on purpose**. It is the only source that reads real environment variables (via `${?VAR}`), and it is the mechanism by which a deployed environment configures the service. Because an unset `${?VAR}` causes typesafe-config to drop that key from the source entirely, local development still falls through to the dev files below it.

The local files are `optional = true` only so a checkout without `application-instagram.conf` still starts. **They are packaged inside the jar**, so they are present in every environment including production — never rely on their absence for correctness.

### Database TLS

`DatabaseConfig.parseJdbcUrl` appends `sslmode=require` to `DATABASE_URL` whenever the host isn't a loopback address (`localhost`, `127.*`, `::1`) and the URL doesn't already specify a mode - the PostgreSQL JDBC driver's own default (`prefer`) silently downgrades to an unencrypted connection if the server doesn't offer TLS, which is the wrong failure mode for anything not on localhost. This is deliberately `require`, not `verify-full`: several managed Postgres providers terminate TLS with a certificate the JVM's default trust store can't validate, and `verify-full` would turn that into a startup outage this class has no way to anticipate per-provider. A deployment that wants hostname/CA verification can still opt in with `?sslmode=verify-full` in `DATABASE_URL` itself - `withEnforcedSsl` leaves an already-present `sslmode=` untouched. Applies identically whether `DATABASE_URL` arrives as `postgres://...` or already-`jdbc:postgresql://...`.

### Config file roles

- **`application.conf`** (per-service, tracked in git) — the schema/defaults, using `${?VAR}` (optional substitution) for anything a deployed environment should set via a real env var. A field left unset here **and** unset in every override is a hard startup failure, because the corresponding Kotlin config field is non-nullable — that's the fail-fast behavior, no code needed to enforce it.
- **`application-local.conf`** (per-service, tracked in git) — shared, non-secret local dev defaults (database, S3/MinIO, port) matching `docker-compose.yml`'s dev credentials, plus `presentation-service`'s override of `uiEnabled` back to `true` (its code default is `false` - see "Defensive HTTP behavior" below). Lives in `src/main/resources` next to `application.conf`.
- **`ingestion-service/config/application-instagram.conf`** (**gitignored**) — real Instagram credentials (`accessToken`, `businessAccountId`) plus the operator-chosen `adminToken`/`readToken` secrets for local development. It lives **outside** `src/main/resources` deliberately: anything under a resource root is packaged into the jar and the container image, so real credentials placed there would ship with the build. It is loaded with `PropertySource.file(...)` relative to the `ingestion-service/` working directory. Copy the commented template and fill in real values; never commit this file, and never move it back under `src/`.

**Important:** a substitution like `${?DATABASE_URL}` inside `application.conf` is resolved by typesafe-config *before* Hoplite ever merges sources, and only against real OS environment variables — **not** JVM system properties. If you're ever tempted to inject config via `System.setProperty(...)` from Gradle (e.g. in a custom `run` task), it will silently fail to reach a forked `JavaExec` process; use the task's `environment(...)`, or better, add another layered `.conf` file the way `application-local.conf` does.

## Defensive HTTP behavior

`presentation-service`'s `Main.kt` wraps `appWithDocsRedirect` in two filters, applied to every route including static assets and `/docs`: `SecurityHeaders.filter.then(rateLimiter.filter)`, with `SecurityHeaders` outermost so its response headers land even on a `RateLimiter`-issued `429` (the inner filter short-circuits before the real handler runs; the outer filter's post-processing still runs on whatever response comes back). Keep this ordering if you touch it - reversing it would mean a rate-limited response skips the security headers.

- **`RateLimiter`** (`ratelimit/RateLimiter.kt`) is a fixed-window counter keyed by the first hop of `X-Forwarded-For`, falling back to one shared bucket when that header is absent - fine for this deployment shape (always single-instance, per AGENTS.md elsewhere) but a real gap for an unproxied deployment. `maxRequestsPerWindow` comes from `PresentationConfig.rateLimitPerMinute` (`RATE_LIMIT_PER_MINUTE`, default 120). No external store - if this service is ever run as more than one instance, the limit becomes per-instance, not global.
- **`SecurityHeaders`** (`security/SecurityHeaders.kt`) sets `X-Content-Type-Options`, `X-Frame-Options`, `Strict-Transport-Security` on every response, and a `Content-Security-Policy` on everything *except* `/docs*` (Swagger UI's own internals aren't controlled by this codebase, so a strict CSP there risks silently breaking it). The CSP's `img-src`/`media-src` stay open (`*`) on purpose - gallery media is genuinely cross-origin (presigned URLs against whatever S3-compatible endpoint this deployment uses). If you add a new static asset or inline script/style to the bundled UI (`public/index.html`/`app.js`), it must stay same-origin or the CSP needs a matching update.
- **`UI_ENABLED` defaults to `false` in code** (`PresentationConfig.uiEnabled`), inverted from its previous default - the bundled admin UI has no login of its own, so a deployment must opt in rather than serve an admin surface by accident. `application-local.conf` overrides it back to `true` for local dev convenience.

## OpenAPI contract navigation

`presentation-service`'s routes are declared with `http4k-api-openapi`'s `contract { }` DSL, one `*Routes` class per resource group (`routes/GalleryRoutes.kt`, `routes/AdminCatalogRoutes.kt`), using `KotlinxSerialization.autoBody<T>()` lenses for request/response bodies. To add a route: declare it as a private `ContractRoute`-returning function, add its lenses/`meta{}` block there, and include it in that class's `routes()`. A path segment (e.g. `{accountId}`) is an `org.http4k.lens.Path.of("name")` lens combined into the path template via `/` — each literal segment appended *after* a path lens also becomes a positional (ignorable, name it `_`) parameter in the curried `to { a, _ -> { request -> ... } }` handler; only segments before the first path lens can be a single plain base-path string. Every route class - `GalleryRoutes` included, now that gallery reads are per-account too - uses the same no-op-filter `Security` pattern: `meta { security = readBearerSecurity }` (or `adminBearerSecurity`, both in `routes/AccountAuth.kt`) documents the scheme in the generated OpenAPI spec without enforcing anything itself (`BearerAuthSecurity(Filter { next -> next }, "...")`), because the real check - per-account, resolved from the `{accountId}` path segment - happens inline via `authorizeAccount(...)` wrapping the handler body. http4k's `ContractRouteMatcher` reads `RouteMeta.security` and would apply a *real* `Security`'s filter ahead of the handler, but a fixed-token filter can't express "look up this account's own token," which is why every route here takes the no-op-filter-plus-inline-check shape instead of a genuine `Security`.

**The OpenAPI renderer uses Jackson, not KotlinxSerialization** — `Main.kt`'s `OpenApi3(ApiInfo("Knurl", "v1.0"), Jackson)`, with `http4k-format-jackson` as a `presentation-service`-only dependency. This is deliberate, not an inconsistency: route bodies still marshal via `KotlinxSerialization.autoBody<T>()` everywhere, exactly as before. kotlinx.serialization's reflection can't reliably build JSON schemas from example values for this OpenAPI module (documented http4k limitation - Jackson is the only fully-supported option for the contract/schema side); using `KotlinxSerialization` there previously made `GET /openapi.json` 500 (`emptyList()`/nullable-field examples crashed the schema walker, then a deeper `Serializer for class 'Ref' is not found` even after fixing those). Swap the renderer's `Jackson` argument back to `KotlinxSerialization` only if you're deliberately reverting this and are prepared to hit that again.

`GET /docs` serves a Swagger UI (`org.http4k.contract.ui.swaggerUiLite { url = "/openapi.json" }`, mounted alongside the `contract { }` app via `routes(app, docs)` in `Main.kt` - it's a separate `RoutingHttpHandler`, not part of the `contract` block itself, since `swaggerUiLite` isn't a `ContractRoute`).

## Pagination

Every list endpoint returns the envelope `{ data, pagination: { totalRecords, currentPage, totalPages, links } }` — `GalleryListResponse`, `GalleryResponse` and `AdminCatalogResponse` all follow it, and a new one should too. The shared pieces live in `presentation-service/.../routes/Pagination.kt`:

- **`MAX_PAGE_SIZE` (50) is the cap for every endpoint**, so clients see one consistent limit. A route clamps with `limitQuery(request).coerceIn(1, MAX_PAGE_SIZE)`; don't reintroduce a per-route magic number.
- **`paginationMeta(request, page)` builds the links.** They are *relative* (path + query), derived from `request.uri`, which is why this service still needs no base-URL config and why the spec can keep `servers: [{ url: "/" }]`. Every incoming query parameter is preserved and only `page` is rewritten, so a client following `next` keeps its sort and filters. If absolute links are ever required, that is a new config field plus an `application.conf` entry — not a `Host`-header guess.
- **`Page.of` (in `shared-domain`) owns the paging math** and is shared by both repositories. It clamps the requested page into `1..totalPages` rather than erroring (matching the `limit` clamp), reports `totalPages >= 1` even for an empty result set, and skips the row query entirely when nothing matched. Routes report `Page.currentPage`, the *effective* page, never what the client asked for.
- **Any paginated query needs a total order.** `ORDER BY timestamp DESC` alone is not one — `timestamp`/`view_count` are not unique, and offset paging over a partial order lets Postgres return a tied row on two pages or on neither. Both `findPage` queries append the primary key as a tiebreaker, and `V1__init_instagram_aggregator.sql` carries composite indexes matching those exact orderings. Same reasoning as `findEvictionCandidates`.
- **A `COUNT(*)` must filter identically to the rows it describes.** `CatalogRepository` routes both through `catalogFilterClause`/`bindCatalogFilter` so they cannot drift; filters go in `CatalogFilter` rather than as loose parameters for the same reason.
- **Filtering belongs server-side, before paging** — a filter has to describe the whole collection, not whichever page loaded. The one exception is the admin UI's "pending" filter, which is unsaved browser state the server cannot know about.
- The example-value constraint above applies to envelope fields too: `examplePagination(path)` populates `prev`/`next` even though both are genuinely null at the range boundaries, because a null example crashes the schema generator. The generated schema still marks them optional.

## Testing

Kotest (`FunSpec` style) across all three modules, run via `./gradlew test` (or `build`). **Use MockK for collaborators** — `mockk`/`every`/`verify`/`slot`, wired in once for every module in the root `build.gradle.kts`. Don't hand-roll fakes, recording lists, or throwing-stub oracles; older tests that still do are being converted as they're touched. Keep MockWebServer where the HTTP client itself is under test (`HttpCredentialSourceTest`, `InstagramAccessTokenProvidersTest`): mocking away the client would mock away the bounds, TLS rules and redaction that are the point of those tests.

Tests only cover logic that doesn't require live Postgres/S3/Graph API credentials (URL parsing, the shortcode regex, `BearerToken` extraction/comparison, `verifyAccountToken` and `AccountCredentialStore`, `RateLimiter` with an injectable `Clock`, retention-window math, `Presigner` signing/TTL behavior — presigning is a pure local SigV4 computation, no network needed) — there is no live-integration test suite in this repo by default. The one exception is `presentation-service`'s `PresignerMinioIntegrationTest`, gated behind `S3_INTEGRATION_TEST=true` so `./gradlew build` still passes without it: start the local bucket (`docker-compose up -d minio minio-init`), then run `S3_INTEGRATION_TEST=true ./gradlew :presentation-service:test` to verify a plain unsigned GET against MinIO is denied while a presigned GET succeeds. Follow this same gating pattern for any other test that needs live infrastructure.

**Route-level tests that must never reach the database** (`GalleryRoutePathBindingTest` is the main example) use a `NeverConnectDataSource` whose every method throws, so a handler reaching real repository code is a test failure rather than a connection error. Since `authorizeAccount` needs *some* resolution of the bearer token before any route-specific logic runs, these tests supply their own `VerifyAccountToken` instead of a real one — otherwise every request would throw at the auth step regardless of whether the thing actually under test (path binding) was correct. Note that auth no longer touches the database at all (`AccountCredentialStore` is in-memory), so this is now only about the *route handler's* repository calls.
