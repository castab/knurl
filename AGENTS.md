# AGENTS.md — Knurl

Context-seeding notes for AI coding agents working in this repo. Read this before making structural changes.

## Hard constraint: low-memory streaming

Both services are *intended* to deploy under a **128MB heap** (`-Xmx128m`, raised from 64MB to give the catalog thumbnail fetch's bounded concurrency headroom — see `SyncPipeline.fetchThumbnailsConcurrently`). **This flag is not set anywhere in this repository** — there is no `applicationDefaultJvmArgs`, Dockerfile or platform descriptor here, so it must be configured on the deployment platform (e.g. as `JAVA_TOOL_OPTIONS=-Xmx128m`). Treat the budget as a binding design constraint regardless of whether the flag is currently applied, because the code is written for it. `ingestion-service`'s HikariCP pool is capped at `maximumPoolSize = 2` / `minimumIdle = 1` (see `shared-domain/.../config/DatabaseSettings.kt`) for the same reason — **do not raise these** without re-checking the memory budget first. *Bounded* coroutine concurrency via a `Semaphore` + the shared `Dispatchers.IO` dispatcher is fine (see `runEviction`/`fetchThumbnailsConcurrently` for the established pattern) — don't add a dedicated/unbounded thread pool or unbounded coroutine concurrency.

**Never buffer a full media payload in a `ByteArray`/`ByteArrayOutputStream`.** Specifically:

- Video: `MediaProcessor.processVideoPassthrough` streams the OkHttp response body directly into the S3 `RequestBody` when `Content-Length` is known. If it isn't (chunked/unknown-length CDN response), it spills to a local temp file (disk, not heap) and uploads from that file — this is the one sanctioned fallback, not a buffering shortcut. Don't "simplify" this by reading the whole video into a `ByteArray` first.
- Images: `MediaProcessor.processImage`/`processThumbnail` decode the source image into memory via Scrimage, produce two WebP variants at 80% quality — a 400×400 grid thumbnail (`squareVariant`, scale-and-center-crop, because every grid cell that consumes it is a fixed `aspect-ratio: 1 / 1`) and an 800px detail image (`boundedVariant`, scaled to fit inside an 800×800 box with the source aspect ratio intact, so at most 800×800 and never upscaled) — and upload the *compressed output only* (tens of KB) as bytes. This is a **documented, bounded exception** — any resize operation requires an in-memory raster at some point. The bound is enforced in `MediaProcessor.downloadImage`, which rejects a source whose declared `Content-Length` exceeds `MAX_SOURCE_IMAGE_BYTES` before decoding; a decoded raster is roughly `width * height * 4` bytes and is otherwise unbounded. Don't try to eliminate the exception; don't remove that ceiling; don't add more image variants without checking the memory cost.

If you're adding a new remote-asset code path, follow the same pattern: OkHttp response `.byteStream()` piped straight into the AWS SDK's streaming `RequestBody`, never fully materialized first.

## Architectural boundaries

- **`presentation-service` issues zero database writes** other than the two analytics counters in `POST /api/v1/accounts/{accountId}/gallery/track` and the `selected` flag toggled by `PATCH /api/v1/admin/accounts/{accountId}/catalog/selections`. It never runs Flyway migrations and never calls the Meta Graph API.
- **`ingestion-service` never opens an HTTP listener** or accepts inbound traffic. It owns the schema — it's the only service that calls `DatabaseConfig.runMigrations`. This is why admin curation flows through `presentation-service` writing a flag in the shared database rather than `ingestion-service` exposing an API of its own — see "Multi-account model" below.
- **`shared-domain` has zero HTTP/JSON-framework dependency.** It doesn't know about http4k, kotlinx.serialization, or Hoplite. `presentation-service` defines its own `@Serializable` response DTOs (`routes/GalleryRoutes.kt`) and maps domain models to them explicitly — don't add serialization annotations to `knurl.domain.models.*`.
- **No application framework.** No Spring Boot, Micronaut, Ratpack, or DI container. Both `Main.kt` files manually construct and wire every collaborator (`HikariDataSource`, `Jdbi`, `OkHttpClient`, `S3Client`, repositories) by hand. Keep it that way — don't introduce a DI library or component-scanning.

## IDs and the database

- `instagram_posts.id` is a **surrogate** primary key — `UUID PRIMARY KEY DEFAULT uuidv7()`, generated by Postgres (18+, native function, no extension). Application code never invents this value; it's read back from the database.
- `instagram_posts.instagram_media_id` is the **natural key** from Meta's Graph API. It's what `SyncPipeline` upserts against (`ON CONFLICT (instagram_media_id)`) and what S3 object key prefixes are built from (`posts/{instagram_media_id}/...`) — this is deliberate, since the media id is known before a database row exists and the surrogate `id` isn't. It and `instagram_media_catalog.shortcode` stay **globally unique**, not composite-keyed with an account, since Meta's ids/shortcodes are unique platform-wide.
- The Kotlin domain type for `id` is `kotlin.uuid.Uuid` (the stable stdlib type, not `java.util.UUID`). JDBI doesn't support it natively — `shared-domain/.../config/KotlinUuidSupport.kt` registers the bridging `ArgumentFactory`/`ColumnMapper`. If you add another `Uuid`-typed column, this bridge already covers it; you don't need to register anything per-repository.
- `InstagramPostRepository.upsert` takes an `InstagramPostUpsert` (no `id`/`createdAt` fields), not the full `InstagramPost` — those two columns are always left to their Postgres defaults.
- `instagram_posts`, `instagram_media_catalog`, and `auth_config` all carry an `instagram_account_id` column now (see "Multi-account model" below) — any new table holding per-account data should follow the same pattern rather than assuming a single global tenant.

## Multi-account model

This schema and both services support multiple Instagram accounts sharing one database, with different tenancy shapes per service:

- **`ingestion-service` is one-process-per-account.** Each instance is configured with exactly one `instagram.businessAccountId` (+ its own `accessToken`/`adminToken`) and only ever reads/writes rows scoped to that account (`SyncPipeline`'s `targetUserId` constructor field is threaded through every repository call). Nothing stops running several instances against several accounts against the same Postgres database.
- **`presentation-service` is genuinely multi-tenant** — a single deployment serves every account that's been registered, with `accountId` (the Graph API business account id — public, non-secret, safe in a URL) as a path segment: `GET /api/v1/accounts/{accountId}/gallery`, `GET/PATCH /api/v1/admin/accounts/{accountId}/catalog[/selections]`.
- **`instagram_accounts`** (`instagram_account_id PK`, `admin_token`) is the tenant registry. A row is (re)written by `AccountRepository.register(...)` in `ingestion-service`'s `Main.kt` on every startup — `admin_token` always gets overwritten from current config, which is also how an operator rotates it. `admin_token` is stored in plaintext, consistent with `auth_config.access_token` already being plaintext.
- **Per-account admin auth, not the global one.** `presentation-service`'s admin catalog routes do **not** use the shared `BearerAuth`/`config.apiBearerToken` (that's only for `POST .../gallery/track`'s anti-abuse check). Instead each request's `accountId` path segment is used to look up that account's own `admin_token` via `AccountRepository.findAdminToken(accountId)`, then compared against the request's bearer token with `BearerToken.matches` (`presentation-service/.../auth/BearerAuth.kt`) — `404` for an unknown account, `401` for a real account with the wrong token. **Never reuse one token across accounts** here; that's the whole point of per-account tokens.
- `sync_configurations` (`max_recent_count`/`max_view_count`) stays **global, not per-account** — every account's retention eviction applies the same numeric limits independently within its own post pool (`InstagramPostRepository.findEvictionCandidates(accountId, ...)` scopes the ranking query, not the limits themselves). The candidate query also excludes any post whose catalog row is still `selected = TRUE`: curation outranks retention, because evicting a still-selected post would only cause `SyncPipeline` to re-download it next cycle. `is_pinned` is read by that query but has no write path anywhere in this repo — it is a manual-SQL-only escape hatch.

## Configuration

Both services load a typed config object from layered HOCON `.conf` resources via Hoplite — see `PresentationConfig`/`IngestionConfig`. **Don't reintroduce scattered `System.getenv(...)` calls** — add a field to the relevant config data class and reference it in a `.conf` file instead.

Hoplite's `addPropertySource` order is priority order: **the first source added wins** when a key is present in more than one, merged per key (not per file). Each `Main.kt` adds sources highest-priority-first:

- `ingestion-service`: `application.conf` (highest) → `application-instagram.conf` → `application-local.conf` (lowest)
- `presentation-service`: `application.conf` (highest) → `application-local.conf` (lowest)

`application.conf` is highest priority **on purpose**. It is the only source that reads real environment variables (via `${?VAR}`), and it is the mechanism by which a deployed environment configures the service. Because an unset `${?VAR}` causes typesafe-config to drop that key from the source entirely, local development still falls through to the dev files below it.

The local files are `optional = true` only so a checkout without `application-instagram.conf` still starts. **They are packaged inside the jar**, so they are present in every environment including production — never rely on their absence for correctness.

### Config file roles

- **`application.conf`** (per-service, tracked in git) — the schema/defaults, using `${?VAR}` (optional substitution) for anything a deployed environment should set via a real env var. A field left unset here **and** unset in every override is a hard startup failure, because the corresponding Kotlin config field is non-nullable — that's the fail-fast behavior, no code needed to enforce it.
- **`application-local.conf`** (per-service, tracked in git) — shared, non-secret local dev defaults (database, S3/MinIO, port, API token) matching `docker-compose.yml`'s dev credentials. Lives in `src/main/resources` next to `application.conf`.
- **`ingestion-service/config/application-instagram.conf`** (**gitignored**) — real Instagram credentials (`accessToken`, `businessAccountId`) plus the operator-chosen `adminToken` secret for local development. It lives **outside** `src/main/resources` deliberately: anything under a resource root is packaged into the jar and the container image, so real credentials placed there would ship with the build. It is loaded with `PropertySource.file(...)` relative to the `ingestion-service/` working directory. Copy the commented template and fill in real values; never commit this file, and never move it back under `src/`.

**Important:** a substitution like `${?DATABASE_URL}` inside `application.conf` is resolved by typesafe-config *before* Hoplite ever merges sources, and only against real OS environment variables — **not** JVM system properties. If you're ever tempted to inject config via `System.setProperty(...)` from Gradle (e.g. in a custom `run` task), it will silently fail to reach a forked `JavaExec` process; use the task's `environment(...)`, or better, add another layered `.conf` file the way `application-local.conf` does.

## OpenAPI contract navigation

`presentation-service`'s routes are declared with `http4k-api-openapi`'s `contract { }` DSL, one `*Routes` class per resource group (`routes/GalleryRoutes.kt`, `routes/AdminCatalogRoutes.kt`), using `KotlinxSerialization.autoBody<T>()` lenses for request/response bodies. To add a route: declare it as a private `ContractRoute`-returning function, add its lenses/`meta{}` block there, and include it in that class's `routes()`. A path segment (e.g. `{accountId}`) is an `org.http4k.lens.Path.of("name")` lens combined into the path template via `/` — each literal segment appended *after* a path lens also becomes a positional (ignorable, name it `_`) parameter in the curried `to { a, _ -> { request -> ... } }` handler; only segments before the first path lens can be a single plain base-path string. The Bearer-auth boundary on `GalleryRoutes` is applied per-route by assigning `security = bearerAuth.security` inside that route's `meta { }` block — it is *not* a blanket filter over the whole contract, and it is *not* a hand-composed `bearerAuth.filter.then(handler)`. http4k's `ContractRouteMatcher` reads `RouteMeta.security` and applies that `Security`'s filter ahead of the handler, falling back to the contract-level `security` only when the route does not set its own. That is why `AdminCatalogRoutes` can pass a deliberately no-op filter to `BearerAuthSecurity` — it needs the OpenAPI scheme description without the enforcement, because its real check is per-account and inline. `AdminCatalogRoutes` doesn't use that filter at all; its auth is per-account and inline (see "Multi-account model" above).

**The OpenAPI renderer uses Jackson, not KotlinxSerialization** — `Main.kt`'s `OpenApi3(ApiInfo("Knurl", "v1.0"), Jackson)`, with `http4k-format-jackson` as a `presentation-service`-only dependency. This is deliberate, not an inconsistency: route bodies still marshal via `KotlinxSerialization.autoBody<T>()` everywhere, exactly as before. kotlinx.serialization's reflection can't reliably build JSON schemas from example values for this OpenAPI module (documented http4k limitation - Jackson is the only fully-supported option for the contract/schema side); using `KotlinxSerialization` there previously made `GET /openapi.json` 500 (`emptyList()`/nullable-field examples crashed the schema walker, then a deeper `Serializer for class 'Ref' is not found` even after fixing those). Swap the renderer's `Jackson` argument back to `KotlinxSerialization` only if you're deliberately reverting this and are prepared to hit that again.

`GET /docs` serves a Swagger UI (`org.http4k.contract.ui.swaggerUiLite { url = "/openapi.json" }`, mounted alongside the `contract { }` app via `routes(app, docs)` in `Main.kt` - it's a separate `RoutingHttpHandler`, not part of the `contract` block itself, since `swaggerUiLite` isn't a `ContractRoute`).

## Pagination

Every list endpoint returns the envelope `{ data, pagination: { totalRecords, currentPage, totalPages, links } }` — `GalleryResponse` and `AdminCatalogResponse` both follow it, and a new one should too. The shared pieces live in `presentation-service/.../routes/Pagination.kt`:

- **`MAX_PAGE_SIZE` (50) is the cap for every endpoint**, so clients see one consistent limit. A route clamps with `limitQuery(request).coerceIn(1, MAX_PAGE_SIZE)`; don't reintroduce a per-route magic number.
- **`paginationMeta(request, page)` builds the links.** They are *relative* (path + query), derived from `request.uri`, which is why this service still needs no base-URL config and why the spec can keep `servers: [{ url: "/" }]`. Every incoming query parameter is preserved and only `page` is rewritten, so a client following `next` keeps its sort and filters. If absolute links are ever required, that is a new config field plus an `application.conf` entry — not a `Host`-header guess.
- **`Page.of` (in `shared-domain`) owns the paging math** and is shared by both repositories. It clamps the requested page into `1..totalPages` rather than erroring (matching the `limit` clamp), reports `totalPages >= 1` even for an empty result set, and skips the row query entirely when nothing matched. Routes report `Page.currentPage`, the *effective* page, never what the client asked for.
- **Any paginated query needs a total order.** `ORDER BY timestamp DESC` alone is not one — `timestamp`/`view_count` are not unique, and offset paging over a partial order lets Postgres return a tied row on two pages or on neither. Both `findPage` queries append the primary key as a tiebreaker, and `V2__pagination_indexes.sql` carries composite indexes matching those exact orderings. Same reasoning as `findEvictionCandidates`.
- **A `COUNT(*)` must filter identically to the rows it describes.** `CatalogRepository` routes both through `catalogFilterClause`/`bindCatalogFilter` so they cannot drift; filters go in `CatalogFilter` rather than as loose parameters for the same reason.
- **Filtering belongs server-side, before paging** — a filter has to describe the whole collection, not whichever page loaded. The one exception is the admin UI's "pending" filter, which is unsaved browser state the server cannot know about.
- The example-value constraint above applies to envelope fields too: `examplePagination(path)` populates `prev`/`next` even though both are genuinely null at the range boundaries, because a null example crashes the schema generator. The generated schema still marks them optional.

## Testing

Kotest (`FunSpec` style) across all three modules, run via `./gradlew test` (or `build`). Tests only cover logic that doesn't require live Postgres/S3/Graph API credentials (URL parsing, the shortcode regex, the Bearer filter, retention-window math, `Presigner` signing/TTL behavior — presigning is a pure local SigV4 computation, no network needed) — there is no live-integration test suite in this repo by default. The one exception is `presentation-service`'s `PresignerMinioIntegrationTest`, gated behind `S3_INTEGRATION_TEST=true` so `./gradlew build` still passes without it: start the local bucket (`docker-compose up -d minio minio-init`), then run `S3_INTEGRATION_TEST=true ./gradlew :presentation-service:test` to verify a plain unsigned GET against MinIO is denied while a presigned GET succeeds. Follow this same gating pattern for any other test that needs live infrastructure.
